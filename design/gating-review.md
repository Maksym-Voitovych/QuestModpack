# Серверна модель блокування 48 епох

Це проєкт вимог до інтеграції, а не готовий перевірений скрипт. Команди Game Stages та підтримку CraftTweaker нижче підтверджує опис користувача; наявність конкретних аддонів, їхні API для NeoForge 1.21.1 та поведінку в запущеному сервері ще треба перевірити за JAR, конфігураціями й журналами. Експорт реєстрів підтверджує ідентифікатори контенту, але не ці можливості.

## 1. Що саме гарантує Game Stages

Game Stages зберігає й перевіряє стадії гравця. Сам по собі він не доводить блокування рецептів, обладнання, вимірів, EMC, луту чи автоматичних машин. Прихована глава FTB Quests або запис JEI — лише інтерфейс. Для строгої прогресії потрібні серверні обмеження кожного способу отримання та використання критичного контенту.

У наданому списку 293 JAR та серед 333 записів `mods.json` експорту не знайдено stage-related mod ID. Це не доводить їх відсутність у поточному інстансі: користувач повідомив про пізніше встановлення, яке могло бути після експорту. Експорт містить 27 964 записи реєстру предметів, але не надає JAR, конфігурацій, вихідних KubeJS-скриптів чи FTB Quests. Потрібні їхні точні назви/версії та перевірка завантаження; не підставляти API старого Forge у NeoForge 1.21.1.

Відомі з повідомлення користувача адміністративні команди: `/gamestage add|remove <player> <stage> [silent]`, `check`, `info`, `clear`, `all`, `reload`; advancement trigger `gamestages:has_stage`; CraftTweaker `player.addGameStage(...)`, `hasGameStage(...)` і `mods.gamestages.StageHelper`. Це не встановлює автоматично еквівалентний виклик із KubeJS. Не вигадувати назви подій, recipe-stage builders чи callbacks FTB Quests.

## 2. Стан епохи без циклічної залежності

Позначення `open_01`…`open_48`, `proof_01`…`proof_48`, `done_01`…`done_48` — власні назви майбутньої реалізації. Вони не є вбудованими назвами API.

Для кожної епохи N сервер виконує таку послідовність:

1. Відкрити епоху 1 під час створення кампанії; епоху N>1 — лише за збереженим `done_(N−1)`.
2. Дозволити обов’язкові завдання епохи N тільки за `open_N`.
3. Перевірити всі обов’язкові технологічні, магічні й дослідницькі завдання, окрім фінального ключа. Лише тоді встановити `proof_N`.
4. Дозволити крафт ключа N за `open_N + proof_N`. Для N>1 рецепт також споживає рівно один ключ N−1.
5. Фінальне завдання не споживає ключ N: воно перевіряє власний успішний крафт, прив’язку до кампанії та попередні обов’язкові завдання.
6. Завершити фінальний квест, встановити `done_N`, а потім `open_(N+1)`. Для N=48 установити завершення кампанії без вигаданої епохи 49.

Завдання «завершити всю епоху» не може бути умовою крафту її ключа, якщо воно включає сам ключ: це глухий кут. Фінальний квест залежить від усіх обов’язкових вузлів через AND; режим OR, optional і залежність лише від одного довільного квеста тут заборонені. Передача готового ключа без власних доказів не завершує епоху.

## 3. Єдині дозволені функції ключів

Ключі мають рівно дві функції: завершити фінальний квест/відкрити наступну главу та бути спожитим інгредієнтом наступного ключа. Вони не є каталізаторами, нагородами за побічні квести, паливом, валютою, фокусами, частинами машин або компонентами побутових рецептів.

Для ключа N<48 повинен існувати лише один рецепт-споживач: ключ N+1. Ключ 48 не має рецептів-споживачів. Звичайні рецепти дозволено блокувати за стадіями без додавання фізичних ключів у їхні інгредієнти. Якщо потрібно ускладнити машини, застосовувати звичайні маготехнічні матеріали, які не виконують роль ключів.

Ключі виключити з EMC, обміну, декрафту, дроблення, плавлення, реплікації, луту, торгівлі, пакетних універсальних конвертерів та автоматичного навчання шаблонів. Вони не повинні мати альтернативних тегових рецептів. Крафт ключа — серверна операція гравця/команди; generic autocrafter або fake player не замінює підтвердження обов’язкових квестів.

У даних перевіряти: ключ N−1 зустрічається серед інгредієнтів лише рецепта ключа N; ключ N не входить у власний рецепт; усі неклю́чові інгредієнти доступні не пізніше епохи N; не вимагати предмета, для виробництва якого вже потрібен ключ N або контент N+1.

Втрата ключа не повинна псувати кампанію назавжди. Пропонована політика: захищений слот/видача після смерті через перевірену реалізацію або адміністративне відновлення за журналом успішного крафту. Не додавати звичайний рецепт відновлення, який використовує ключ у третій функції. Не припускати, що soulbound-поведінка вже є. Дублікат фізичного ключа сам по собі не створює `proof` чи `done`.

## 4. Команди, особиста прогресія та команди гравців

Рекомендована кампанія — спільна прогресія команди FTB Teams, відповідна командним квестам FTB Quests. Це свідоме правило: вступ до розвиненої команди надає її прогрес. Якщо потрібна персональна кампанія, обидві системи треба налаштувати персонально; не поєднувати командне завершення квестів із незалежним особистим ключем без явної політики.

Серверний журнал кампанії зберігає UUID команди, виконані обов’язкові докази, найвищу завершену епоху та успішні крафти ключів. Конкретний механізм збереження обрати після перевірки API; файл не припускає існування готового KubeJS team-ledger API.

Стадії гравця — проєкція цього журналу. Під час входу, зміни команди та відновлення сервера перераховувати тільки стадії з власним префіксом збірки, зберігаючи чужі стадії. Вихід із команди не має залишати її стадії у нового учасника іншої кампанії. Прив’язку ключа до команди слід перевіряти під час крафту/квесту, але сам NBT не є надійним джерелом виконаних завдань.

Команда `/gamestage all`, операторський режим, creative і адміністративне завершення квестів — навмисні адміністративні обходи. Не використовувати їх як звичайні нагороди та не надавати гравцям відповідні права. Відкат прогресу — окрема адміністративна транзакція: стадії, квести й журнал мають залишатися узгодженими.

## 5. Матриця обов’язкового серверного контролю

| Канал обходу | Необхідна політика |
|---|---|
| Ручний крафт, shift-click, книга рецептів | Перевірка стадії на сервері до видачі результату; забрати оригінальний та всі альтернативні рецепти, якщо вводиться новий рецепт |
| Машинні рецепти | Окремо перевіряти кожен тип рецепта/машини; стадія ручного крафту не блокує переплавлення, збагачення, ритуал або infusion |
| Вже поставлений блок | Заборонити встановлення, відкриття меню й запуск відповідної машини без стадії; приховування предмета недостатньо |
| Лут, нагороди, торгівля | Видалити ранні джерела або замінити дозволеним лутом; ключі не генеруються тут |
| Підбирання, скрині, сумки, посилки | Перевірка інвентарного доступу й використання пізніх предметів; без мовчазного видалення речей — повертати/карантинувати з повідомленням |
| Надягання, Curios, пасивні ефекти | Заборонити екіпірування/активацію; перевіряти також вже вдягнені Gobber/Relics/Artifacts/Apotheosis предмети |
| Подорожі вимірами | Серверна перевірка всіх порталів, телепортів, ракет, предметів повернення та сторонніх способів входу |
| ProjectE та AppliedE | Перевірка вивчення/виведення предметів, портативних планшетів, мережевих EMC-інтерфейсів і старих знань; ключі та контрольні компоненти без EMC |
| Mystical Agriculture, Botany Pots, симуляції мобів | Не допустити ранніх насіння, рецептів горщиків, віртуального луту, boss-моделей чи есенцій, що обходять реальні обов’язкові цілі |
| Торгівля між командами | Передача предмета не передає стадію; використання перевіряє стадію одержувача |
| AE2/Integrated Dynamics/Modular Routers та інша автоматизація | Перевірка власника мережі/операції; зберігання дозволеного матеріалу не надає права його використовувати |
| Fake players | Відмова за відсутності дозволеної й перевіреної прив’язки до команди; не видавати усім fake players усі стадії |
| Розрив з’єднання, перезапуск, death, team change | Ідемпотентна звірка журналу, стадій та квестів; жодна з цих подій не повинна самостійно видавати нову епоху |

Рецептна ціна — частина балансу, а не повна реалізація доступу. Навіть дуже дорогий рецепт не блокує знайдений у луті артефакт, подарований реактор чи скопійовану машину.

## 6. Невизначений власник автоматизації

Game Stages індивідуальний, а встановлена машина може не мати облікового власника. Не можна автоматично прирівнювати її до найближчого гравця: це дає обхід. Варіанти реалізації потрібно підтвердити в конкретних модах:

- підтримуване серверне зіставлення машини/мережі з UUID команди та перевірка її поточного стану;
- заборона автоматичного крафту ключів і контроль запуску пізніх машин через охоронний серверний мод/перевірений аддон;
- якщо наявні інструменти не вміють зупинити потрібний машинний рецепт, додаткова серверна інтеграція є необхідним блокером, а не виконаною умовою.

Глобальна серверна стадія не замінює особисту/командну прогресію у світі з кількома незалежними командами. Вона дозволяє всім користуватися досягненнями першої команди й суперечить суворому доступу для кожної кампанії.

## 7. Якість доказів у квестах

Предметне завдання з режимом «вже є в інвентарі» підходить для побутових ресурсів, але не доводить власний запуск виробництва чи перемогу. Для обов’язкових віх вимагати підтверджену серверну подію крафту/виробництва, advancement, kill або серверну перевірку стану. Конкретні підтримувані FTB Quests task types перевірити за встановленою версією; де немає потрібного типу — потрібен перевірений міст інтеграції.

Перший запуск реактора, обробка партії руди, отримання реальної аури/мани й перемога над босом — різні докази. Не замінювати їх усі предметною карткою з довільним прапорцем. Звичайні виробничі матеріали можна передавати всередині команди. Побічні/декоративні завдання не блокують ключ, якщо явно позначені необов’язковими.

Повторний крафт, синхронізація входу та повторний виклик обробника не повинні повторно видавати нагороди або пропускати епоху. Подія крафту наступного ключа допускається лише після повністю зафіксованого `done_N`.

## 8. Збереження наявного прогресу та ідентифікаторів

В експорті вже є предмети доказів `kubejs:aia2_*` та рецепти в гілці `recipes/kubejs/aia2_v07*/`. Вони є свідченням наявної роботи, а не дозволом її замінити чи приписати нові функції невідомим предметам. Нові ключі `kubejs:aia2_epoch_key_01`…`kubejs:aia2_epoch_key_48` — запроєктовані ID; реєстр експорту не підтверджує їх існування.

Перед реалізацією потрібні інвентаризація точних старих ID/recipe ID/quest ID, резервна копія світу та правил прогресії й таблиця переходу старих доказів до нових віх. Не видаляти всі `aia2_*` чи `aia2_v07*` масовим шаблоном. Не повторно реєструвати вже зайнятий ID. Старий proof-предмет сам по собі не є доказом, що гравець завершив усі нові обов’язкові завдання; автоматичний перенос потребує явної й перевіреної політики.

## 9. Перевірки перед заявою про суворе блокування

Мінімальний інтеграційний сценарій на реальному сервері: чистий гравець → спроби доступу до N+1 → виконання всіх віх N → один крафт ключа → збереження ключа після фінального квесту → відкриття N+1 → споживання попереднього ключа тільки в наступному ключі → перезапуск → повторна звірка.

Додаткові негативні сценарії: видати готовий ключ через адміністратора без віх; передати ключ з іншої команди; отримати пізню машину через лут; використовувати вже встановлену чужу машину; вивести ресурс через EMC/AppliedE; запустити autocrafter/fake player; увійти у вимір стороннім телепортом; змінити команду; втратити ключ; обробити повторний event. У всіх випадках заздалегідь визначити очікуваний дозвіл/відмову й перевірити його на сервері.

Статична перевірка даних може довести лінійний граф, відсутність циклів інгредієнтів, покриття епох і єдине використання ключів. Вона не доводить блокування автоматизації, JEI, предметних ефектів чи подій сервера. Поки такі перевірки не виконані, результат слід називати специфікацією прогресії, а не готовою перевіреною реалізацією.
