# Журнал виробничих ключів — аудит збереження0.4.22

База: `35a4d5d` /0.4.21-alpha. Файл `aia2_key_production_v1.dat` містить
історичні виробничі докази команд. Це не інвентар ключів і не FTB completion.
Схема1 та простір48епох ×2гілки =96канонічних доказів залишаються чинними.
Жоден доказ не можна створити через міграцію предметного прогресу.

## Підтверджена першопричина

Досліджено фактичний NeoForge21.1.264 /Minecraft1.21.1 SDK. Точні SHA SDK,
source entries і line references збережено у
`content/research/evidence/key_journal_v11/manifest.json` та чотирьох
`minecraft_api/*.json`. Повні Minecraft sources до пакета не копіюються.

`DimensionDataStorage.readSavedData` перехоплює Exception як під час читання
файлу, так і в десеріалізаторі. Після цього повертається null. `get` кешує
навіть null; `computeIfAbsent` не розрізняє відсутній файл і невдале читання
та встановлює новий порожній SavedData. Тому виняток у loader сам по собі
не захищає попередню історію. Пізніше справжній крафт може позначити нову
порожню структуру dirty й замінити нею старий журнал.

SavedData записується лише коли dirty=true. Його compound serializer
викликається перед передачею даних IO worker. Відмова blocked serializer
перериває цей шлях до файлового запису. Sentinel також не повинен
позначатися dirty або підміняти собою порожній встановлений журнал.

## Контракт збереження

Читання має спочатку використати `get`, а після null перевірити існування
відповідного файлу. Для спільного overworld-журналу це
`world-root/data/aia2_key_production_v1.dat`. Наявний нечитабельний файл має
залишатися недоторканим; відсутність доказу та помилка журналу не дають
права виготовити новий ключ або безкоштовно завершити перехід.

Правильний новий порожній журнал спочатку існує лише в пам’яті. Його
встановлення в DimensionDataStorage та dirty-запис дозволені тільки після
довіреного завершення виробничого процесу. Configure/read/clearRuntime не
створюють історію. Очищення runtime-кешу не видаляє правильний SavedData
і не скидає вже створені96виробничих доказів.

Типи NBT перевіряються явно: `getInt` може конвертувати інші numeric tags,
`getCompound` повертає порожній compound за неправильного типу. Для схеми
потрібен INT1, для true proof — BYTE1, для teams і кожної команди — COMPOUND.
Попередній writer записував лише true. Старий loader ігнорував false-значення;
тепер false, інший числовий тип або BYTE зі значенням, відмінним від 1,
закривають увесь некоректний журнал для читання доказів і нових записів.
Це навмисне посилення перевірки, без видалення чи виправлення вихідного файла.
Межі запису та читання збігаються: 16384 команди, 96 рядків доказів на команду,
128 символів назви команди та 64 символи рядка доказу. Доказ, який уже є при межі, залишається
ідемпотентним. Обмеження64, використане для іншого механічного журналу,
не можна переносити на цей журнал із96канонічними ключами.

## Історичні неканонічні рядки

Попередній writer завжди записував `8:tech`, без leading zero чи знака.
Попередній loader перевіряв `Integer.parseInt`, але зберігав сирий рядок:
`08:tech` або `+8:tech` могли пройти перевірку та залишитися неактивними,
оскільки `hasProof(8, "tech")` шукав саме `8:tech`.
Автоматичне перетворення такого рядка на канонічний надало б новий дозвіл.
Воно не є сумісним перенесенням історії. Реалізація зберігає parse-valid
неканонічні рядки буквально та неактивними, якщо вони вкладаються у зазначені
межі. Лише подальше справжнє виробництво може додати окремий канонічний доказ,
не видаляючи старий рядок. Якщо 96 рядків уже зайнято, новий 97-й рядок
відхиляється до зміни журналу. Цю поведінку фіксують регресії; автоматичного
скидання, очищення файла або надання canonical proof немає.

## Інсталятор та межі доказів

Інсталятор працює з kubejs/, config/ і власним companion JAR. Він не
перераховує світи чи player/team save files і не мігрує цей журнал.
Старий власний JAR та змінювані конфіги резервуються перед встановленням;
наявний FTB data.snbt зберігається. За пошкодження журналу відновлення
виконується з перевіреної власної копії при зупиненій грі.

`tests/test_key_journal_sources_v11.py` завжди перевіряє чотири portable fact
файли та їхні SHA. За наявності точного зовнішнього SDK він окремо перевіряє
SHA самого SDK і дев’яти source entries; відсутність SDK позначається як
непроведена upstream-перевірка, а не успішне відтворення Minecraft.

Source audit підтверджує описаний lifecycle. Host-тести зі змодельованим
сховищем, actual Minecraft NBT/SavedData/restart і повний інстанс із
optional-модами — різні рівні перевірки. Їхні результати слід читати у
checkpoint verification report; цей документ не заявляє успішного запуску
повного клієнта або вимірювання TPS.
